# 被験者実験用 GUI の計画（たたき台）

2026-11-08 作成。詰めポケ Ver1 の問題を被験者に解いてもらい、評価を集めるための GUI の計画をまとめる。
まだ決めていないことは「未決」と書き、決まったら書き換えていく。

## 0. 実装の状況（2026-11-08）

モックアップを `tsumepoke/gui/` に作った。動かし方と、確かめたこと・確かめていないことは `tsumepoke/gui/README.md` にある。
G1〜G4 と G6（プレイデモ）は一通り動く形になっていて、G5（予備実験）はまだ行っていない。
作るときに、ユーザーから次の2つの方針をもらった（2026-11-08）。

- 情報や機能を増やすか迷ったら増やす。できれば設定で ON・OFF できるようにする。後から削るほうが、後から足すより楽なため。
- 特性・運・状態異常などを後で足しやすい作りにする。エンジンとのやり取りをアダプタ1か所にまとめ、設定項目は一覧から設定画面を作る形にした（`tsumepoke/gui/README.md` の「新しい要素を足すとき」）。

## 1. 前提（2026-11-08 に決めたこと）

- 実施する場所：研究室の自分の PC。被験者に来てもらい、その PC のブラウザで解いてもらう。結果もその PC に保存する。
- 評価の項目：今の `rate.js` と同じにする（面白さ・難しさ・意外性の5段階、コメント、自動で記録する時間・失敗回数・あきらめたか）。
- 被験者：ポケモン対戦の初心者も含む。ルールの説明と練習問題が要る。
- 問題の割り当て：未決（6章）。どちらの方式にも対応できる作りにする。

## 2. 作り方

### 2.1 構成

```
ブラウザ（画面の表示と入力だけ）
   ↕  HTTP（localhost）
Node のサーバ（tsumepoke/v1 の engine.js・solver.js をそのまま使う）
   ↕
results/ に被験者ごとの記録を保存
```

- 対戦の処理と相手の手の選び方は、サーバ側で今の `engine.js` と `solver.js` をそのまま使う。ブラウザ側に移すと、`data.js` が PS の図鑑を読む部分を作り直すことになり、CLI と結果がずれる心配も出るため。
- サーバは Node に最初から入っている `http` モジュールで書き、npm のパッケージは足さない。研究室の PC で `node` を1つ動かすだけで使えるようにする。
- 画面は HTML と JavaScript だけで書き、ビルドの手順は作らない。
- 研究室の PC の中だけで使うので、サーバは `localhost` からの接続しか受け付けない。

### 2.2 置き場所

`tsumepoke/gui/` に置いた。Ver1 以外のエンジンにも使えるように、`v1` の外に出している。表のファイルの役割は `tsumepoke/gui/README.md` のほうが新しい。

| ファイル | 役割 |
| --- | --- |
| `server.js` | サーバ。問題の配信、手の受け付け、記録の保存 |
| `public/index.html` ほか | 画面 |
| `sets/` | 問題セット（6章） |
| `results/` | 被験者ごとの記録。公開しないので `.gitignore` に入れる |

`play.js` の表示用の関数（日本語名、ダメージの計算）は、サーバから使えるように一部を切り出す。

## 3. 実験の流れと画面

1. **受付**：実験者が被験者 ID を入れて始める。同じ ID で入り直すと、続きから再開する。
2. **事前アンケート**：ポケモン対戦の経験など（未決、7章）。
3. **ルールの説明**：次の内容を、図や例を入れて説明する。
   - 「N ターン以内に、相手がどう動いても確実に勝つ」手順を探す問題であること
   - 相手は、こちらの勝ちを一番遅らせる手を選んでくること
   - ダメージは、自分の技は最低乱数、相手の技は最高乱数で固定していること。急所・命中・特性・持ち物はないこと
   - 素早さが同じときは相手が先に動くこと、交代の扱い
   - タイプ相性の表（3.2 節のメニューからいつでも開ける）
   - 操作の紹介：プレイデモで、実際の画面を動かしながら見せる（3.3 節、後回しでよい）
4. **練習問題**：1ターンと2ターンの問題を1〜2問。本番の記録とは分けて保存する。
5. **本番**：問題を解く画面と評価の画面を、問題の数だけ繰り返す。
6. **終了**：お礼の画面。

### 3.1 問題を解く画面

配置は Pokemon Showdown の対戦画面を土台にする（2026-11-08 にユーザーと決めた）。
真似するのは配置と見せ方だけで、Showdown の画面のコードとポケモンの画像は使わない。

```
┌──────────────────────────────────────┬──────────────────┐
│ 残り 3 ターン以内に確実に勝つ          [相性表] [ダメージ表] │
├──────────────────────────────────────┼──────────────────┤
│                    相手：○●●（控え）  │ バトルログ         │
│                ┌────────────────┐    │ 1ターン目          │
│                │ マフィティフ あく│    │  あなたの…！       │
│                │ ████████░░ 155/155│   │  相手の…！        │
│                │ 素早さ 105        │    │                  │
│                └────────────────┘    │                  │
│ ┌────────────────┐                   │                  │
│ │ ドードリオ ノーマル/ひこう│         │                  │
│ │ ███████░░░ 114/135 │               │                  │
│ │ 素早さ 130（先に動く）│             │                  │
│ └────────────────┘  あなた：●●●（控え）│                  │
├──────────────────────────────────────┴──────────────────┤
│ 技：[ドリルライナー じめん 36(23%)] [でんこうせっか ノーマル 27(17%) 優先+1] … │
│ 交代：[パルキア 150/165] [ハリーセン 116/140]                                    │
└───────────────────────────────────────────────────────────┘
```

- 場：相手のポケモンを右上、自分のポケモンを左下に置く。名前、タイプ（タイプの色の札）、HP（数値とバー。残りに応じて緑→黄→赤）、素早さを出す。
- 控え：両者とも場の近くに小さく並べ、倒れたポケモンは暗くする。マウスを乗せると、そのポケモンの HP・タイプ・素早さ・技が出る。
- 技のボタン：技のタイプの色に塗る。技の名前、タイプ、威力、優先度、相手の場のポケモンへのダメージ（数値と割合）を書く。
- 交代のボタン：控えのポケモンの名前と HP を書く。
- バトルログ：画面の右側に、そのターンに起きたことを文章で上から順に足していく。
- 残りのターン数：画面の上に、目立つ文字で出す。
- 倒れたあとに出すポケモンを選ぶとき：交代のボタンだけを出す。
- 失敗したとき：「もう一度挑戦する」と「あきらめて解答を見る」を選べる。
- 正解したあと、またはあきらめたあと：解答の手順と、正解以外の初手への相手の受けを見られる。

#### ダメージ表（2026-11-08 にユーザーから要望）

技のボタンには相手の場のポケモンへのダメージしか出ないので、控えも含めた相手のすべてのポケモンへのダメージを確かめられる表を別に用意する。
相手が交代でかわしてくる問題では、交代先にどれだけ入るかが読みの材料になる。
普段は閉じておき、見たいときにだけ開く形にする（見ずに解きたい人の邪魔にならないため）。

案：画面上の「ダメージ表」ボタンで開く表。下の値は id 1576（`puzzles_upto8.json` の8ターンの問題）で計算したもので、割合は最大 HP に対する値になる。

| あなたのポケモン・技 | 相手 マフィティフ（場） | 相手 シェイミ（控え） | 相手 エーフィ（控え） |
| --- | --- | --- | --- |
| ドードリオ：ドリルライナー | 36（23%） | 17（10%） | 50（36%） |
| ドードリオ：でんこうせっか | 27（17%） | 25（14%） | 37（26%） |
| パルキア：ハイドロポンプ | 118（76%） | 44（25%） | 93（66%） |
| … | … | … | … |

- 行はこちらの全ポケモンの全技、列は相手の全ポケモンにする。控えのポケモンの技も入れる（交代してから撃つ場合の参考になる）。
- 切り替えで、向きを逆にした表（相手の全技から、こちらの全ポケモンへのダメージ）も出せるようにする。
- 倒せる値（残り HP 以上）には印を付けるかどうかは未決。付けると読みの手間が減り、問題の難しさが変わる。
- 開いた回数を記録する（4章）。

別案：相手の控えのポケモンをクリックすると、技のボタンのダメージがそのポケモンへの値に切り替わる。
表より画面が散らからないが、全体を一度に見比べにくい。どちらにするか（両方付けるか）は、G1 で試して決める。

### 3.2 いつでも開けるメニュー

画面の上に常に置き、問題を解いている途中でも開けるようにする。開いても時間の計測は止めない。

- **タイプ相性表**：18 タイプ × 18 タイプの表。攻撃側のタイプを選ぶと、その行だけを強調する。PS のタイプ相性のデータ（`data.js` が読んでいるもの）から作る。
- **ルールの確認**：3章の3で説明した内容を、もう一度読める。
- **ダメージ表**：3.1 節のもの。

開いた回数を記録する（4章）。

### 3.3 プレイデモによる操作紹介（後回しでよい）

ルールの説明のあとに、簡単な問題を1問、自動で解いてみせる。
実際の問題画面の上で、「技のボタンを押す → ログに結果が出る → 次のターンに進む」流れを、吹き出しで説明しながら1手ずつ進める。
被験者が「次へ」を押すと次の手に進む形にして、読む速さを被験者に任せる。
デモに使う問題は、交代と倒れたあとの選択が両方出てくる2ターン程度の問題がよい（未決）。

### 3.4 評価の画面

- 面白さ・難しさ・意外性を、`rate.js` と同じ目安の文言つきで5段階から選ぶ
- コメントの欄（空でもよい）
- 3つすべてを選ぶまで次へ進めない

## 4. 記録すること

1問ごとに、`rate.js` と同じ項目を保存する。

- 問題の id、ターン数、出題の順番
- 正解したか、失敗した回数、あきらめたか、かかった秒数
- 面白さ、難しさ、意外性、コメント、評価した日時

GUI で新しく足す項目：

- 被験者 ID、問題セットの名前
- **各ターンに選んだ手の記録**（挑戦ごと）。どこで間違えたか、どれだけ迷ったかを後から見られる
- 解答の画面を開いたか
- ダメージ表、タイプ相性表、ルールの確認を開いた回数

保存は1問ごとに行い、途中でブラウザを閉じても、そこまでの記録は残す。全員分をまとめた CSV を書き出すコマンドも作る。

## 5. 作る順番

| 段階 | 内容 | 確かめ方 |
| --- | --- | --- |
| G1 | サーバと、問題を解く画面（評価なし）。ダメージ表を含む | 同じ手を選んだとき、`play.js` と同じ結果になるか。ターンごとの応答の速さ |
| G2 | 評価の画面と記録の保存、再開 | 途中で閉じて開き直したときに続きから始まるか |
| G3 | ルールの説明、練習問題、いつでも開けるメニュー（タイプ相性表、ルールの確認） | 自分で通して読む。可能なら初心者の知り合いに試してもらう |
| G4 | 問題セットと割り当て、CSV の書き出し | 2〜3人分の ID で試し、順番と記録が正しいか |
| G5 | 予備実験（自分か研究室の人で通しで1回） | 所要時間、分かりにくい説明、操作の不具合を洗い出す |
| G6 | プレイデモによる操作紹介（後回しでよい） | 初心者が説明だけで操作できるようになるか |

## 6. 問題の割り当て（未決）

次の2つの方式に対応できるようにしておき、どちらを使うかは後で決める。

- **全員同じ問題**：問題セットを1つ用意し、出題の順番だけ被験者ごとに変える（被験者 ID を乱数の種にしてシャッフル）。人による評価の違いを比べやすい。
- **被験者ごとに別の問題**：`rate.js` と同じ選び方（ターン数ごとに乱数で選び、同じ系列は1問まで）を、被験者ごとに違う種で行う。全体として多くの問題を評価できるが、1問あたりの評価の数は減る。

問題セットは `sets/` に JSON で置き、問題の局面も写しておく。`rate.js` と同じく、`puzzles.json` を作り直しても実験の記録は使えるようにする。

## 7. 決めること

- [x] ポケモンの画像を出すか：設定で切り替えられるようにした（2026-11-08）。`public/sprites/` に画像があれば出す。画像を使ってよいかは、まだ確かめていない
