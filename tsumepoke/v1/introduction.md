# 詰めポケ Ver1 の解説

2026-10-12 作成。`tsumepoke/v1/` のプログラムが何を参考に、どんな手法で問題を作って解いているのかを、研究の文書として説明する。
使い方の一覧と取り決めの細目は同じフォルダの `README.md` に、先行研究の要約は `refs_summary.md`（非公開）にある。

このプログラムは、ポケモンのシングルバトルを乱数のないモデルに簡略化し、その上で「相手がどう動いても N ターン以内に必ず勝てて、しかも最初の一手が1通りに決まる局面」を自動で作るものになっている。
問題を解く部分（ソルバ）は AND/OR 木の全幅探索で、問題を作る部分は、ランダム生成で短い問題を集めてから1ターンずつ長くする延長法を使っている。
5ターンまでの問題 1,416 問を、約7分半で作ることができた。

---

## 1. 位置づけ

詰将棋や詰めガイスターのように、交互に手を指すゲームの「詰め問題」の自動生成には、すでに研究の積み重ねがある。
一方で、ポケモンのように両者が同時に行動を選ぶゲームについては、詰め問題を定義して作った例が `refs/` の資料の中には見当たらなかった。
Ver1 は、この同時手番の詰め問題を「まず動くものとして作ってみる」ための最初の版にあたる。

扱う範囲は、ユーザーとの相談（2026-10-12）で次のように絞った。
確率の要素はすべて取り除き、急所は出ず、技は外れず、ダメージ乱数は回答者（p1）の技は最低値、相手（p2）の技は最高値に固定している。
特性・持ち物・状態異常・能力ランクも扱わない。
乱数を「回答者に不利な側」へ倒しているので、Ver1 で詰みと判定された局面は、実際のポケモンでもダメージ乱数がどう出ても勝てる局面になっている（急所・外れ・追加効果を無視している分は除く）。

## 2. 参考にした先行研究と、取り入れたもの

| 先行研究 | 取り入れたもの |
|---|---|
| 石井（2020、JAIST 修士論文、詰めガイスター） | 研究全体の流れ（定義 → ソルバ → ランダム生成と逆順生成 → 評価）。延長法を「候補を作ってから検証する」形で行うこと。最短手数を反復深化で求めること |
| 川上ら（2020、詰めガイスターの後退解析） | 一意解をどこまで求めるかを、問題の定義の一部として明示すること（準一意解の考え方） |
| 高峰ら（2025、ガイスターのエンドゲーム DB） | 勝ちの種類を「誰の方策が先に決まるか」という量化子の並び（∃p1 ∀p2）で定義する書き方 |
| 小西（2023、JAIST 修士論文、簡易ポケモンの読み合い AI） | PS を直接使わず、ポケモンを簡略化したモデルを自作して高速に探索する方針 |
| tanuki-tsume-shogi（詰将棋生成アプリ） | 生成と検証を分ける設計。延長法（N 手の問題から N+2 手を作る）と、その多様性が元の問題に縛られるという注意点 |
| KomoringHeights（詰将棋ソルバ） | 最短手数を、上限を変えながら探索し直して確定させる考え方 |
| 石飛（2013）、高橋竜太郎ら（2018） | Ver1 では使っていない。面白さ・難しさの推定（証明数、特徴量）を入れる段階で参照する予定 |

詰将棋の慣習のうち「余詰め」の扱いは、面談（2026-08-19）での池田先生の提案に従った。
初手だけは唯一解とし、2ターン目以降は正解が複数あってもよいことにしている。

## 3. 対戦モデル（engine.js）

### 3.1 PS から借りたものと、自作したもの

Pokemon Showdown（PS、commit `b1156ff`）から借りたのは、図鑑のデータ、技のデータ、タイプ相性表、それにダメージと能力値の計算式だけになっている。
1ターンの処理（行動順、ダメージ、倒れたときの交代）は自作した。
自作した理由は速さにある。
PS の対戦エンジンで1ターン進めるには約 0.45ms かかり（`PLAN.md` の 2026-09-17 の記録）、`practice/e2_solver.js` では3ターン先を読むのに43秒かかっていた。
自作エンジンでは、5ターンの問題1問を最後まで解くのに平均 64ms で済んでいる（4章）。

### 3.2 ルール

- 各側のポケモンは1〜3匹で、全員レベル50、個体値31、努力値0、性格補正なしにしてある。
- 技は、PS のランダムバトル（第9世代）の型に含まれる技のうち、威力が一定で確実に起こる追加効果を持たない攻撃技 192 個から、1匹につき最大4つを選ぶ。ポケモンは、こうした技を2つ以上持てる 335 匹を候補にした。
- 行動は「技を使う」か「控えと交代する」のどちらかで、交代は技より先に行われる。
- 技の順番は、優先度（例：アクアジェットは +1）が高いほうが先で、同じなら素早さが高いほうが先になる。素早さも同じときは p2 を先にした。
- 先に動いた技で相手が倒れると、倒れたポケモンの技は出ない。倒れた側は控えから次のポケモンを選んで出し、ターンが終わる。
- 確率で起こる追加効果（例：10まんボルトの 10% のまひ）は起こらないものとして扱う。

### 3.3 PS との一致の確認

自作したダメージ計算は、PS の `getDamage` と 20,000 通りの組み合わせで比べ、1件も違わなかった。
1ターンの処理も、ランダムな 1,974 局面で PS を1ターン動かした結果と一致している。
この比べ方が甘くないことを確かめるため、PS 側の乱数をわざと 85 から 86 にずらしたところ、326 件の不一致が出た。
2ターン以上続けた流れは PS と突き合わせていないので、ここは未確認として残っている。

## 4. 問題を解く方法（solver.js）

### 4.1 同時手番を AND/OR 木にする

同時手番のゲームでは、両者が相手の手を知らずに行動を選ぶ。
Ver1 では、これを「p1 が先に手を決め、p2 はそれを見てから手を選ぶ」という交互手番に置き換えて探索している。
p2 に p1 の手を見せるのは p2 を有利にする変更なので、この変形のもとで p1 が勝てるなら、本来の同時手番でも p1 は必ず勝てる。
逆に、本来のゲームで確率1で勝てる手があるなら、その手は p2 に見られても勝てる（確率1の勝ちは、相手の手の読みに頼らないから）。
したがって確定勝ちを判定する限り、この変形で答えは変わらないということになる。
この議論は `e2.SolverDescription.md` にまとめてあり、ガイスターの「紫駒」（隠れた情報を常に攻め方に不利な側へ倒す）とも同じ考え方になっている。

置き換えたあとの木では、1ターンが次の2段になる。

```
OR ノード：p1 が手を選ぶ（どれか1つで勝てればよい）
  └ AND ノード：p2 が手を選ぶ（どの手に対しても勝てなければならない）
       └ ポケモンが倒れたとき：p2 の交代先は AND、p1 の交代先は OR
```

Ver1 には乱数がないので、PS を使っていたころの e2_solver.js にあった「乱数の結果の枝」（1ターンで数十〜数千本）はなくなった。

### 4.2 判定と最短ターン数

中心になる関数は `winWithin(局面, n)` で、「p1 が n ターン以内に、相手の手によらず勝てるか」を返す。
深さ n の全幅探索に、「残りターン数｜局面」をキーにした置換表を付けている。
最短ターン数は、n を 1, 2, 3, … と増やしながら `winWithin` を呼び、初めて真になった n として求める。
石井（2020）が df-pn に反復深化を組み合わせて最短手数を求めたのと同じ方法になっている。
置換表は n の値をまたいで使い回すので、深さを1つ増やすたびに浅い部分を最初から探し直す無駄は少ない。

### 4.3 問題として成り立つかの判定

局面を受け取って次の順に調べる（`Solver.analyze`）。

1. 最短ターン数 N を求める（上限は「作る問題の最大ターン数 + 1」）。上限までに勝てなければ問題にならない。
2. p1 の初手ごとに、その手から勝つまでの最短ターン数を求める。
3. ちょうど N ターンで勝てる初手が1つだけなら、問題として採用する。

N より長くかかって勝てる初手（迂回）は、詰将棋の慣習に合わせて余詰めとは数えていない。
5ターンの問題 173 問のうち 122 問に、こうした迂回の初手が含まれていた。

### 4.4 出題時の相手の手

出題するときの相手は、p1 の勝ちを一番遅らせる手を選ぶ（詰将棋の「最長の受け」と同じ）。
勝ちを逃れられる手があれば、勝つまでのターン数が無限大になるので、その手が選ばれることになる。

### 4.5 解く速さ

各ターン数の問題から50問ずつを選び、`analyze` を走らせた時間を測った（2026-10-12、この PC で計測）。

| ターン数 | 1問の平均 | 最大 | 1問あたりのターン処理の回数（平均） |
|---|---|---|---|
| 1 | 1.0 ms | 19 ms | 68 |
| 2 | 3.3 ms | 26 ms | 373 |
| 3 | 17.9 ms | 158 ms | 1,947 |
| 4 | 34.6 ms | 223 ms | 3,731 |
| 5 | 63.9 ms | 416 ms | 6,945 |

1ターン増えるごとに、処理の回数はおよそ2〜5倍に増えている。
df-pn のような「有望な枝から調べる」工夫は、この速さで足りている間は入れていない。

## 5. 問題を作る方法（generate.js）

### 5.1 初期問題：ランダム生成

延長法には元になる問題が要るので、最初はランダムに局面を作り、短い問題を集めた。

1. 各側のポケモンの数を1〜3匹のどれかに決め、335 匹の候補から種族を、その種族の技の候補から最大4つの技をランダムに選ぶ。
2. 各ポケモンの HP を、最大 HP の 5%〜100% の間でランダムに決める。
3. 4.3 節の判定にかけ、2ターン以内で詰み、初手が唯一の局面だけを残す。

乱数の種1で 4,000 局面を作り、395 問（約 9.9%）が残った。
内訳は1ターンの問題が 224 問、2ターンの問題が 171 問になっている。
最大5ターンの設定で作ったときは 32.6 秒かかった（最大3ターンの設定では 6.6 秒）。
詰まない局面を「6ターン以内には勝てない」と確かめるところに時間の大半を使っている、と考えている。

### 5.2 延長法：1ターンずつ長くする

N ターンの問題から N+1 ターンの問題を作る手順は次のとおりにした。

1. N ターンの問題の局面に、「1ターン前はこうだった」と見なせる変更を1〜2回加えた候補を作る。変更は次の5種類から選ぶ。
   - 相手の場のポケモンの HP を増やす（前のターンに受けたダメージを戻す）。選ばれやすさは他の2倍にした。
   - 相手のポケモンを1匹足して場に出す（前のターンに倒されたポケモンを戻す）。
   - 相手の場のポケモンを控えと入れ替える（前のターンの交代を戻す）。
   - 回答者の場のポケモンの HP を増やす。
   - 回答者の場のポケモンを控えと入れ替える。
2. 候補を 4.3 節の判定にかけ、ちょうど N+1 ターンで詰み、初手が唯一なら採用する。
3. だめなら別の候補を作り直す（1問あたり最大 60 回）。

1ターン前の局面を厳密に逆算しようとすると、両者の手の組み合わせ（最大で 6×6 通り）と、そのターンに与えたダメージの両方を推定することになり、候補がふくれあがる。
池田先生も面談で、同時手番での逆算は効率が悪そうだと指摘していた。
そこで Ver1 では、石井（2020）や tanuki-tsume-shogi と同じく「それらしい候補を作ってからソルバで確かめる」方式にした。
厳密な逆算ではないので、作った問題の1ターン目の局面から元の問題の局面へ、実際の手順でたどり着けるとは限らない。

### 5.3 生成の結果と時間

`node tsumepoke/v1/generate.js 5 1`（最大5ターン、乱数の種1）の結果を示す。

| 段階 | 元の問題 | 作れた問題 | 成功した割合 | かかった時間 |
|---|---|---|---|---|
| ランダム生成 | 4,000 局面 | 395 問（1〜2ターン） | 9.9% | 32.6 秒 |
| 1 → 2 ターン | 224 問 | 213 問 | 95% | 7.2 秒 |
| 2 → 3 ターン | 384 問 | 355 問 | 92% | 53.0 秒 |
| 3 → 4 ターン | 355 問 | 280 問 | 79% | 131.2 秒 |
| 4 → 5 ターン | 280 問 | 173 問 | 62% | 226.5 秒 |

合計は 1,416 問（1ターン 224、2ターン 384、3ターン 355、4ターン 280、5ターン 173）で、全体の時間は 7分31秒だった。
長くなるほど成功する割合が下がり、1問を検証する時間も延びている。
6ターン以上の問題も同じ方法で作れるはずだが、試していない。

### 5.4 新しく問題を作るには

`詰めポケ/` のフォルダで次のように実行する。

```
node tsumepoke/v1/generate.js 最大ターン数 乱数の種
例：node tsumepoke/v1/generate.js 5 2
```

結果は `tsumepoke/v1/puzzles.json` に追記され、同じ局面（種族・HP・技・場のポケモンがすべて同じもの）は重複して入らない。
乱数の種を変えれば別の問題が出て、同じ種なら同じ問題が出る。
作り直したいときは `puzzles.json` を消してから実行する。
1回の実行で試す局面の数（4,000）や、延長の試行回数（60 回）は、`generate.js` の先頭の定数で変えられる。

作った問題は次のように確かめられる。

```
node tsumepoke/v1/play.js --list           … 問題の一覧
node tsumepoke/v1/play.js 608              … 出題（失敗したら最初からやり直し）
node tsumepoke/v1/play.js 608 --answer     … 解答と、正解以外の初手への相手の受け
```

## 6. できた問題の例

（id は `generate.js 5 1` で作り直した 2026-10-12 時点の `puzzles.json` のもので、作り直すと変わる。）

id 608（3ターン）は、回答者の Tauros-Paldea-Aqua（HP 121）と Entei、相手の Gardevoir（HP 15）と Clefable（HP 125）の局面になっている。
Gardevoir は、アクアジェットでもアクアブレイクでもストーンエッジでも倒せる。
ところが相手が1ターン目に Clefable へ交代すると、威力の低いアクアジェットやストーンエッジでは3ターン以内に2匹とも倒せなくなる。
正解はアクアブレイクだけで、「目の前の相手は何で倒しても同じ」に見えて、実は相手の交代を読む問題になっている。

id 1246（5ターン）では、回答者の Munkidori に対し、相手は Bellossom・Piloswine・Magearna を持っている。
ヘドロウェーブなら Bellossom を1発で倒せるが、相手が毒技の効かない鋼タイプの Magearna に交代すると空振りになる。
相手は回答者の技に合わせて、効きにくいポケモンへ交代してかわそうとする。きあいだまは3匹のどれにも等倍以上で通るので、撃ち続けるのが正解になる、という構造をしている。

5ターンの問題 173 問のうち 39 問では、正解の初手が交代だった。
一方で、同じ技を押し続けるだけで解ける問題がどのくらい混ざっているかは、まだ数えていない。

## 7. 今の版の限界

- 問題の面白さと難しさは評価していないので、易しすぎる問題やひと目で分かる問題も区別なく入っている。
- 延長法で作った問題は、元の問題と同じ詰み筋を引き継ぎやすい。tanuki-tsume-shogi でも、9手詰 571 問のうち詰み筋が異なるのは 29 種だったと報告されている。Ver1 では詰み筋の重なりを測っていない。
- 急所・外れ・追加効果を「起きない」としているので、実際の対戦で同じ局面になっても、低い確率で負けることがある。
- 2ターン以上続く流れを PS と突き合わせていない（3.3 節）。
- 「回答者の HP を増やす」変更は、問題を易しくする方向にも働く。延長の候補の作り方は、まだ調整していない。

## 8. 今後の研究の展開

### 8.1 問題の質を測る（RQ2）

最初に取り組む候補は、面白さと難しさを数で表すことになると考えている。
石飛（2013）と石井（2020）は、証明数探索の途中の証明数の最大値が、人が感じる難しさと関係することを示した。
Ver1 のソルバを証明数探索（PNS や df-pn）に置き換えれば、同じ量を取り出すことができる。
ほかにも、次のような量が候補になる。

- **紛れの数**：「p2 の手を知っていれば勝てるが、知らないと勝てない」初手の数。同時手番に固有の量で、id 608 のアクアジェットのような「選びたくなる不正解」を数えることになる。
- **浅い読みとの食い違い**：1ターンだけ読むプレイヤーや、一番ダメージの大きい技を選ぶプレイヤーが、正解を選べるかどうか。高橋竜太郎ら（2018）が紹介した大町らの方法や、DeepMind のチェスパズル生成の「意外性」と同じ発想にあたる。
- **要素を外して解き直す判定**：石井（2020）の「赤駒壁利用」の判定と同じく、交代を禁止したり、ある技を消したりして解き直し、問題が成り立たなくなれば、その要素が問題の要になっていると判定できる。池田先生の言う「趣向」を自動で見分ける方法として使える。
- **詰み筋の重なり**：正解の手順が同じ問題を数え、延長法の偏りを測る。

### 8.2 被験者実験

石井（2020）と同じく、ポケモン経験の違う人たちに問題を解いてもらい、面白さ・難しさ・上達に役立つかを5段階で答えてもらう実験が考えられる。
8.1 節の量を特徴量にして評価を推定すれば、良い問題だけを選んで出せるようになる。
石井の実験では、難しすぎる問題は面白いと評価されなかったので、制限時間と難しさの釣り合いも調べる必要がある。

### 8.3 生成方法を広げる

- **狙いを先に決める生成**：「交代読み」「先制技で縛る」のような型を手で用意し、パラメータだけをランダムに埋める。池田先生の「狙い」の案にあたる。
- **あと少しで詰む局面から作る**：詰まない局面のうち、HP や技を少し変えれば詰むものを探し、負け筋を消す方向に変更する。これも池田先生の案で、野下（1996）の簡約操作に近い。
- **実戦の局面から作る**：Showdown の対戦ログから終盤の局面を集め、詰みがあるかを調べる。中間発表の「実戦的な問題」という目的に直結する。

### 8.4 ルールを本物に近づける

Ver1 で取り除いた要素を、問題の趣向として1つずつ戻していく道もある。
きあいのタスキ、先制技、能力ランク、状態異常などを入れると、局面の表し方と探索の量が大きくなる。
そのときは、ソルバを df-pn に置き換えて有望な枝から調べる工夫（KomoringHeights の初期値の見積もりなど）が必要になってくると考えている。
命中率や急所を戻す場合は、「確定勝ち」を「勝率 p 以上」に広げるかどうかが定義の問題になる。
その場合、小西（2023）のように各ターンを行列ゲームとして解く方法が使える。

### 8.5 詰みの定義を理論として整える（RQ1）

「p2 に p1 の手を見せても確定勝ちの判定は変わらない」という性質は、Ver1 の正しさの前提になっている。
これを同時手番ゲーム一般について示し、量化子の並び（∃p1 ∀p2 ∀乱数）で詰みを定義し直せば、研究の成果の1つとして論文に書ける。
高峰ら（2025）のガイスターでの観察（紫駒で勝ちなら必勝、残り7駒以下では逆も成り立った）とも比べられる。
