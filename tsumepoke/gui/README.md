# 詰めポケ 被験者実験用 GUI（モックアップ）

2026-11-08 作成。詰めポケ Ver1 の問題をブラウザで解いてもらい、面白さ・難しさ・意外性の評価を集めるための画面である。
計画と、まだ決めていないことは `tsumepoke/v1/GUI_PLAN.md` にまとめてある。

## 動かし方

`詰めポケ/` のフォルダで次を実行し、表示された `http://localhost:8787/` をブラウザで開く。

```
node tsumepoke/gui/server.js
```

npm のパッケージは使っていない。サーバは同じ PC からの接続だけを受け付ける。

| URL | 内容 |
| --- | --- |
| `http://localhost:8787/` | 受付の画面。被験者 ID と問題セットを選んで始める |
| `http://localhost:8787/#free=1277` | id 1277 を記録なしで解く |
| `http://localhost:8787/#free=7&play=3,1` | id 7 で、ボタンの並びの3番目、1番目の順に手を選んで進める |
| `http://localhost:8787/#free=1277&open=damage` | ダメージ表を開いた状態で始める（`typechart`、`rules`、`settings` も使える） |
| `http://localhost:8787/#demo` | プレイデモを見る |

## 実験の流れ

受付 → 事前アンケート → ルールの説明 → プレイデモ → 練習問題 → 本番（問題を解く → 評価）の繰り返し → 終了、の順に進む。
事前アンケートからプレイデモまでと練習問題は、設定でそれぞれ外せる。
同じ被験者 ID で受付からやり直すと、終わったところの次から再開する。

## ファイル

| ファイル | 役割 |
| --- | --- |
| `server.js` | サーバ。API と画面のファイルを配る |
| `adapters/v1.js` | 詰めポケ Ver1 のエンジンとソルバをつなぐ部分。画面はここが返す形だけを見て表示する |
| `settings_schema.js` | 設定項目の一覧。設定画面はここから自動で作る |
| `sets.js`, `make_set.js` | 問題セットの読み込みと被験者への割り当て、問題セットを作るスクリプト |
| `sets/*.json` | 問題セット。今は `ratings1`（自分で評価した50問）、`sample10`（被験者ごとに各ターン数10問）、`short`（動作確認用の4問）がある |
| `config/rating_items.json` | 評価の項目と5段階の目安の文言 |
| `config/survey_items.json` | 事前アンケートの項目 |
| `config/settings.json` | 設定画面で保存した値（初期値から変えた項目だけが入る） |
| `public/` | 画面（HTML、CSS、JavaScript） |
| `public/sprites/` | ポケモンの画像を置く場所（任意。`git` には入れない） |
| `results/<被験者 ID>.json` | 被験者ごとの記録（`git` には入れない） |

問題セットは次のように作る。

```
node tsumepoke/gui/make_set.js 名前 --ids 9,188,7          # 決めた問題を全員に出す
node tsumepoke/gui/make_set.js 名前 --sample 10             # 被験者ごとにターン数ごとに10問を選ぶ
node tsumepoke/gui/make_set.js 名前 --from-ratings ../v1/ratings_1.json
```

## 記録の中身

`results/<被験者 ID>.json` には、事前アンケートの答え、始めたときの設定の写し、割り当てた問題（局面の写しつき）、1問ごとの結果が入る。
1問ごとの結果は `rate.js` と同じ項目（正解したか、失敗の回数、あきらめたか、秒数、評価、コメント）に、次の3つを足したものになる。

- 挑戦ごとに、各ターンに選んだ手と相手の手（`attempts`）
- 解答を見たか（`answerViewed`）
- ダメージ表、タイプ相性表、ルールを開いた回数と、控えのクリックなどの操作の時刻（`uiCounts`、`uiLog`）

CSV に書き出すスクリプトはまだない。

## 新しい要素を足すとき

特性や状態異常などをエンジンに足すときは、次の順に進めれば画面を作り直さずに済むようにしてある。

1. 新しいエンジン用のアダプタ（`adapters/v2.js` など）を作り、`features` で対応した要素を `true` にする。`node tsumepoke/gui/server.js --engine v2` で切り替えられる。
2. アダプタの `monView` で `status`、`ability`、`item`、`boosts` に値を入れる。画面は、`features` が `true` で設定が ON の要素だけを表示する。
3. 新しい出来事（「やけどのダメージ」など）は、アダプタが `text` に表示用の文を入れて返す。画面は種類を知らなくても、文をそのまま表示する。
4. 新しい設定が要るときは、`settings_schema.js` に1行足す。`requires` に要素の名前を書くと、対応していないエンジンでは灰色になる。

## ポケモンの画像

設定の「ポケモンの画像を出す」を ON にし、`public/sprites/<ポケモンの id>.png` に画像を置くと、その画像を表示する。
id は PS の内部の名前（`garchomp`、`ninetalesalola` など）で、画像がないポケモンはタイプの色の丸と名前の頭文字で表示する。
画像の著作権は任天堂などにあるので、使ってよいかを確かめてから置く。

## 確かめたこと（2026-11-08）

- アダプタの対戦の処理を、`play.js` の出題の処理と比べた。ランダムに選んだ 300 局面で、同じ手を選んだときの相手の手と勝ち負けが、1件も食い違わなかった（そのうち 168 局面は勝ちで終わった）。
- API だけで、被験者の登録、事前アンケート、間違えてからやり直して正解、あきらめて解答を見る、評価の保存、同じ ID での再開までを通した。記録のファイルに、失敗の回数、挑戦ごとの手、解答を見たか、ダメージ表を開いた回数が入ることを確かめた。
- 対応していない設定（状態異常を有効にするなど）を保存しても、初期値に戻ることを確かめた。
- ヘッドレスの Chrome で、受付、問題の画面（始めたとき、正解したとき、失敗したとき）、ダメージ表、タイプ相性表、設定、プレイデモの最初の画面を撮って、表示が崩れていないかを見た。

## まだ確かめていないこと

- 事前アンケート、ルールの説明、練習問題、評価、休憩、終了の画面と、プレイデモの2手目以降は、画面で操作して確かめていない（API と、ブラウザの JavaScript の構文の確認だけ）。
- 制限時間、確認の表示、マウスを乗せたときの説明の表示は、動かしていない。
- 実際のブラウザで、人が操作して通したことはまだない。
